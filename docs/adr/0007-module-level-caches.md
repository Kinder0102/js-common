# 0007 模塊級無界緩存

## 狀態

已接受，但有已知代價。

## 背景

DSL 解析是本倉庫最熱的操作：一次渲染會對幾十上百個元素調用 `createProperty` / `createTemplateHandler` / `createFilter`，而同一模板裏這些字符串**完全相同**。每次重新切分字符串是純浪費。

同時這些模塊是純函數式的，沒有實例可以掛緩存。`DOMHelper` 有實例，但 `createProperty` 是獨立導出的，下游可以單獨用。

## 決策

在模塊作用域放三個緩存，以 DSL 字符串爲鍵：

| 模塊 | 緩存 |
|---|---|
| `js-dsl-factory` | `PROPERTY_CACHE` `TEMPLATE_CACHE` `FILTER_CACHE` |

只增不減，沒有 LRU、沒有上限、沒有清理 API。

## 理由

- 鍵空間由「模板裏寫死的字符串」構成，正常情況下是有限小集合（幾個到幾十個）。
- 加清理策略需要引入淘汰時機（定時？訪問計數？），複雜度遠超收益。
- 模塊級緩存跨實例共享，同一頁面多個 `DOMHelper` 也只需解析一次。

## 後果

這是一個**有意的取捨**，代價必須知曉：

1. **DSL 字符串不要拼接易變數據。** `data-af-value="user.${id}"` 這種動態生成的屬性會以每個不同字符串爲鍵，緩存無界增長。應當寫在模板裏用固定字符串，數據通過 `item` 傳。
2. 緩存的生命週期等於頁面生命週期（ESM 模塊只求值一次），刷新才清。
3. 長駐應用（編輯器、大屏）如果確實需要動態 DSL，請在應用層自己做一層有界緩存，不要把動態串餵給本倉庫。

如果將來出現真實的內存問題，正確做法是給三個緩存加一個共享的 `clear()` 並暴露爲獨立導出，而不是改成自動淘汰——自動淘汰會讓「解析一次」的性能保證失效。屆時另寫 ADR 取代本篇。
